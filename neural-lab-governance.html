01 / Start with the business need

The goal was image-based work.
The obstacle was an unreliable workflow.

I was using local AI models through OpenWebUI for image-based reporting. When images could not be processed, the immediate issue was technical. The operational issue was broader: I could not rely on the workflow to support the task it was meant to perform.

I used Cline to investigate Neural Lab, my local AI environment. The investigation found that the Lab detected image auxiliaries, but its Builder did not pass the selected mmproj into the server request. Discovery in one screen had not translated into a complete execution path.

The questions I needed answered

  • What task is the user trying to complete?
  • What must be true before the output can be used?
  • Who decides when a suggested configuration is acceptable?
  • What evidence lets that person make the decision?
  • How do we preserve the fix for the next session?
My brief was bigger than “make the image load.”

Restore the capability, make compatibility uncertainty visible, protect the existing text-model workflow, and give the operator a reviewable basis for acceptance.

02 / Where I intervened

I challenged the plan before approving execution.

The agent proposed matching the model with an auxiliary file and restoring the missing Builder controls. I paused at the risks. A plausible implementation plan still needed rules for ambiguity, unsupported binaries, and the existing text-only workflow.

Roberto / Before approval · translated excerpt
“Before approving, how can you address the risks identified in the plan in advance?”
Cline / Revised approach · summary

The proposal evolved from risk descriptions into preventive controls and checks: flag ambiguous matches, reject an auxiliary used as a main model, expose unsupported runtime capabilities, and verify that text-only commands remain unchanged.

My next decision set the boundary of autonomy. Confidence could support a recommendation, but the operator would confirm the auxiliary and review a pre-flight check. The agent implemented the agreed rules; I remained responsible for the workflow and its acceptance.

01

I challenged automatic attachment.

The proposal: resolve the missing auxiliary through model matching, with automatic attachment considered for confident matches.

My decision: the system could recommend an auxiliary and explain its confidence. A human would confirm the selection, followed by a vision pre-flight check before release.

The resulting requirement: uncertainty must stay visible. A file in the same directory must not, by itself, establish that the model can process images.

02

I questioned the test itself.

The first version: a background check reused the same image and gave the operator too little visibility into the model’s response.

My request: use a variable bank of red, green, blue, and yellow test images, and show what was sent, what was expected, and what the model actually returned.

The acceptance criterion: I needed to inspect the result directly, including the color swatch, prompt, raw response, HTTP status, response time, and model used.

03 / Investigation and correction

A running interface was only the starting point.

Once the auxiliary workflow was addressed, real testing exposed additional problems. I evaluated the observed behavior while the agent inspected and changed the implementation.

04 / The resulting control loop

Human judgment became part of the process.

From the working session / How the test evolved

I could see the test result.
I could not see what the model was doing.

The first implementation ran a vision check in the background using the same red square. During hands-on validation, I questioned both the visibility of the result and the use of a single fixed image. That conversation changed the acceptance criteria.

Roberto / Observation
“Everything worked in the Lab. The only thing is that, when I click test, the system runs it in the background and the user cannot see how the model behaves.”

Business implication: a status indicator alone did not give the operator enough information to evaluate the output.

Roberto / Question
“Is this image generated by the model itself, or is there a bank of different images so the model does not memorize a single image?”

Acceptance question: was this a meaningful capability check, or simply the same narrow test repeated?

Cline / Finding and implementation

The image was generated by the backend, not by the model. There was no variable bank: each check reused a red square. The concern was a fixed test producing a plausible repeated answer, rather than the model memorizing a newly generated image.

The implementation added four color cases, random selection per execution, and visible evidence: expected color, swatch, prompt, raw answer, HTTP status, response time, and model used.

rule
My acceptance criterion changed.

A background pass/fail indicator was insufficient. I needed varied inputs and enough visible evidence to compare the model’s answer with the image. The four colors below are the test bank that resulted from that intervention.

05 / Evidence and its limits

Claims tied to implementation and validation.

What changed in the product

The vision endpoint contains the four-color bank, a random selection with a fixed test index for repeatable checks, 448px images, and the revised answer budget. Test outcomes can be recorded in server_runs.vision_check when a run is supplied.

The interface exposes the expected color and model response alongside diagnostic feedback, making review possible at the point of use.

What the session reports

The October 20 validation records report 112 backend tests and 35 frontend tests passing, plus human validation through OpenWebUI. These counts describe that recorded session; they are not a live test result from this website.

Project memory, architecture, and product documentation were updated to preserve the decisions and the revised workflow.
